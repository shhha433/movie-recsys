# 双塔召回 + DIN 排序的推荐系统

## 项目简介

在 MovieLens-1M 数据集上实现一套完整的**两阶段推荐链路**：

1. **召回层**：双塔模型 + Faiss，从全库 3883 个物品里快速捞出 top-50
2. **排序层**：DIN 模型，对召回的候选按用户兴趣重新精排

召回层用 4 组对照实验 + 配对 bootstrap 检验选出最优配置；
排序层对比了「平均池化」和「注意力池化」两种用户兴趣建模方式。

**主要结果**：

| 层级 | 结果 |
| --- | --- |
| 召回 | 训练改用余弦相似度后，Recall@50 从 **6.74%** 提升到 **9.42%**（+2.67pp，配对 bootstrap p<0.001） |
| 排序 | 使用注意力加权机制后，test AUC |

## 一、数据集

| 项目 | 说明 |
| --- | --- |
| 名称 | MovieLens-1M（GroupLens / 明尼苏达大学） |
| 来源 | https://grouplens.org/datasets/movielens/1m/ |
| 内容 | 6040 个真实用户、3883 部电影、100 万条真实评分记录（2000–2003 年）；其中被评分过的电影 3706 部 |
| 正样本定义 | 评分 ≥ 4 视为"喜欢"，共 575,281 条交互 |
| 切分方式 | **按时间切分**：前 80% 训练 / 中 10% 验证 / 后 10% 测试 |

**为什么按时间切分**：随机切分会让模型在训练时"看到未来"，离线指标虚高、上线就崩。
本项目用 2000–2003 年的早期数据训练，用后期数据评估，模拟真实的"用过去预测未来"。

### 样本构造

把"用户按时间的观影序列"滑窗成 `(历史, 目标, 标签)` 三元组：

```text
某用户的序列：[M1, M2, M3, M4]
   历史 "M1"     → 目标 M2    label 1      ← 正样本
   历史 "M1"     → 目标 M77   label 0      ← 从全库随机抽的负样本
   历史 "M1 M2"  → 目标 M3    label 1
   历史 "M1 M2"  → 目标 M15   label 0
   ...
```

- 历史序列保留最近 **3** 个物品（`MAX_HISTORY = 3`），进模型时左补 0 补齐到 10 列
- 正负样本比例 1 : 4
- 最终训练样本 **2,274,230 条**

**为什么历史只留 3 条**：这是为控制变量做的取舍——先跑通「召回 → 排序」全链路，历史长度的消融留到后续实验（见「后续计划」）。

## 二、整体架构：召回 → 排序

```text
                       ┌─────────────────────────────────────────┐
   用户 + 待打分候选 → │  召回层（双塔 + Faiss）  全库 3883 → top-50 │
                       └─────────────────────────────────────────┘
                                          ↓
                       ┌─────────────────────────────────────────┐
                       │  排序层（DIN）           top-50 → 精排分数 │
                       └─────────────────────────────────────────┘
```

**为什么必须分两层**：双塔的用户向量必须与候选物品无关，才能离线算好、建索引、用 ANN 检索——
这让召回层只能用「与候选无关」的池化。而排序层的候选物品是输入的一部分，用户表示可以随候选变化。
两层的建模能力不同，能做的事也不同。

---

## 三、召回层：双塔模型

```text
                    ┌──────────────┐
   历史序列 [B, 10]  →  物品 Embedding  →  平均池化  →  MLP  →  用户向量 [B, 32]
                    └──────────────┘                                    ↘
                                                                       内积 → 分数
                    ┌──────────────┐                                    ↗
   候选物品 [B]     →  物品 Embedding  →            MLP  →  物品向量 [B, 32]
                    └──────────────┘
```

用户塔接收用户的历史行为序列，经 Embedding 编码后**对非 padding 位置平均池化**，
再过 MLP 得到用户向量；物品塔接收候选物品 ID，编码后过 MLP 得到物品向量；两者做内积得到分数。

**关键设计点**（面试会问）：

1. **两个塔共用同一张物品 Embedding 表**——历史和目标物品是同一批物品，没必要两张表
2. **`padding_idx=0`**：历史序列用 0 补齐，这个参数让第 0 行恒为 0 且不参与训练，
   所以平均池化时 padding 天然不产生贡献
3. **左补 0**：最近的物品永远在最后一个位置，为将来改用 "last-item pooling" 留了余地
4. **用户塔看不到候选物品**——这不是偷懒，是双塔的定义；否则用户向量无法离线预计算

## 四、排序层：DIN

### 4.1 为什么召回层不能用注意力，排序层可以

用户塔算用户向量时**看不到候选物品**，是双塔存在的理由：只有与候选无关，用户向量才能离线算好、
建 Faiss 索引、做 ANN 检索。所以召回层只能用「与候选无关」的池化——平均、取最近 N 个、时间衰减加权。

排序层不一样：候选物品是它的输入之一，用户表示可以随候选变化。
DIN 的注意力加权就建立在这个自由度上——**要猜他喜不喜欢这部科幻片，就重点看他看过的科幻片**。

（这也是为什么 DIN 不能像双塔那样预计算用户向量：每个候选都要重算一遍。）

### 4.2 模型结构

```text
历史序列 [B, L] ─┬─→ Embedding → h [B, L, d] ──┐
                 │                              ├─→ 加权求和 [B, d] → MLP → 用户向量 [B, 32] ─┐
候选物品 [B] ────┴─→ Embedding → q [B, d] ──────┘                                              │ 内积
                 │                                                                             │ → 分数
                 └─→ 打分网络 q/h/q−h → 注意力权重 [B, L] ─────────────────────────────────────┘

候选物品 [B] ─→ Embedding → 物品塔 MLP → 物品向量 [B, 32] ───────────────────────────────────────┘
```

### 4.3 注意力权重怎么算（三步）

1. 历史向量 `h ∈ [B, L, d]`，候选向量 `q ∈ [B, d]`
2. 打分网络（两层 MLP）吃三段拼接 **`[候选, 历史, 候选 − 历史]`**，输出每个历史位置的分数 `[B, L]`
3. padding 位置先置 `-inf` 再 softmax，得到和为 1 的权重；用它对 `h` 加权求和

**两个容易写错的点**：

- **mask 必须在 softmax 之前**。`softmax(-inf) = 0`，padding 权重正好是 0；如果先 softmax 再置零，
  剩下的权重和就不再等于 1。我第一版就是在这里写错的：拿「分数等于 0」当条件去 mask，
  结果 mask 全 False（分数几乎不可能正好是 0），padding 位置分走了 0.0993 的权重。
- **`padding_idx=0` 让第 0 行 embedding 恒为零**，所以 padding 位置的 `h` 是零向量。
  不 mask 的话它不会把用户向量的方向带偏，但会把真实位置的权重和压到小于 1，
  而且压多少随每个样本的历史长度变化——历史短的样本被压得更狠。

`din.py` 里带了自动自检，会检查「padding 位置权重为 0」「每行权重和为 1」两条硬约束，不通过就不进训练。

## 五、评估方式

| 指标 | 怎么算 | 说明 |
| --- | --- | --- |
| **AUC** | 在「1 正 + 4 负」的候选集上算 | 衡量排序质量（召回层和排序层都用） |
| **Recall@50** | 在全库 3883 个物品里检索 top-50，看目标是否命中 | 衡量**真实召回能力**，只有召回层用 |
| 随机基线 | 50 / 3883 ≈ **1.29%** | Recall@50 的下界参考 |

**为什么两个指标都要**：AUC 只在 5 个候选里排序，Recall@50 要在全库检索——**难度完全不同，
不能互相替代**。我的模型 AUC 0.87，但 Recall@50 只有 6.74%，这个差距是正常的。

**置信区间**：所有指标都用 bootstrap（1000 次重采样）给出 95% 置信区间；
实验之间的比较用**配对 bootstrap** 检验显著性。

**训练用的 loss 和这些指标是两回事**。双塔也是神经网络，参数要靠梯度下降更新，
所以训练时必须有可微的目标函数——本项目用的是 `BCEWithLogitsLoss`，只在**训练集**上算。
AUC 和 Recall@50 不参与参数更新，它们只是衡量"训得好不好"。

| | 在哪算 | 作用 |
| --- | --- | --- |
| loss（BCE） | 训练集，每一步 | **唯一的训练信号**，决定参数往哪走 |
| AUC | 验证集（每个 epoch）、测试集（最后） | 便宜的"体检指标"：看收敛、比模型、粗筛设计选择 |
| Recall@50 | 验证集 / 测试集，训练结束后 | 对得上召回任务的真实指标；要建 Faiss 索引跑全库，贵 |

**AUC 两个阶段都能算，Recall@K 只有召回层有意义**——排序层的输入已经是召回来的那几十个候选，
"从全库检索"这件事在排序层根本不存在，它只负责把这几十个重新排序。

## 六、实验结果

### 6.1 召回层：主结果

| 模型 | valid AUC | test AUC | Recall@50 |
| --- | --- | --- | --- |
| 双塔（内积，均值池化） | 0.8679 | 0.8511 | 6.74% |
| **双塔（余弦，均值池化）** | 0.8139 | 0.7946 | **9.42%** |
| 双塔（训练时余弦，检索时内积，均值池化） | 0.8128 | 0.7967 | 10.57% |

### 6.2 召回层：消融实验（+ 显著性检验）

**实验设置**：同一份训练集（227 万条）、同一份验证集（56,440 个正样本）、同一随机种子，
每次只改一个变量。

| 实验 | 改动 | Recall@50 | vs 基准 | p 值 | 结论 | 召回结果里热门片占比 |
| --- | --- | --- | --- | --- | --- | --- |
| baseline | 均值池化 + 内积 | 6.74% | — | — | 起点 | 24.3% |
| A | 池化改成「取最后一个物品」 | 6.28% | −0.46pp | <0.001 | 显著变差 | — |
| **B** | **余弦训练 + 余弦检索** | **9.42%** | **+2.67pp** | **<0.001** | **显著变好** | 52.0% |
| **B2** | **余弦训练 + 内积检索** | **10.57%** | **+3.83pp** | **<0.001** | **显著变好** | 62.6% |
| C | 池化改写成 masked mean | 6.72% | −0.02pp | 0.452 | 不显著（应等价） | — |

### 6.3 排序层：用户兴趣的聚合方式（平均 vs 注意力）

**先说清楚这里在比什么**：比的**不是**「召回模型 vs 排序模型」，而是**同一个排序模型里，
用户塔把历史序列压成一个向量的两种方式**。

| 聚合方式 | 怎么把历史压成用户向量 | 用户塔能看见候选物品吗 |
| --- | --- | --- |
| 平均池化 | 对非 padding 位置求平均 | 不能 |
| 注意力池化（DIN） | 按「与候选的相关度」加权求和 | 能 |

两个模型的其余部分完全一致：同一张物品 Embedding 表、同样形状的 `user_mlp` / `item_mlp`、
同样的内积打分、同一份数据、同一套训练循环。实测参数量 7,424 vs 10,561——
DIN 只多了一个注意力打分网络（`att_mlp`：96→32→1，3,137 个参数）。
**唯一的变量就是聚合方式**，所以两个 AUC 可以直接比。

注意「平均池化」不是双塔的专利。召回层之所以用它，是因为双塔的用户塔看不到候选物品；
排序层没有这个约束，才有资格换成注意力。这是**约束造成的选择**，不是模型归属。

**实验设置**：同一份数据、同一个随机种子、同样的训练轮数和学习率，只换聚合方式。

| 用户塔的聚合方式 | valid AUC | test AUC | 相对基线 |
| --- | --- | --- | --- |
| 平均池化 | 0.8679 | 0.8511 | — |
| 注意力池化（DIN） | 0.8645 | 0.8502 | −0.0009 |

**这个差是真是假**：单个随机种子的结果不足以判断。我在同一配置下用 3 个随机种子各跑了一次
（200k 训练子集，3 轮，验证集/测试集全量）：

| 种子 | 均值池化 | 注意力池化 | 差 |
| --- | --- | --- | --- |
| 42 | 0.7566 | 0.7566 | −0.0001 |
| 7 | 0.7653 | 0.7603 | −0.0051 |
| 2026 | 0.7569 | 0.7527 | −0.0043 |

同一个模型只换随机种子，test AUC 的波动就有 **0.0087**（均值池化）/ **0.0076**（注意力池化），
比两个模型之间的差（平均 **0.0031**）还大。

### 6.4 端到端：把召回和排序真正串起来

6.1–6.3 都是分开评估的——召回用 Recall@K，排序用随机负样本上的 AUC。
但**排序层实际面对的候选不是随机物品，而是召回出来的 top-50**，所以还要串起来评一次：

流程：召回层取 top-50 候选 → 排序层给这 50 个重新打分排序 → 看目标物品排到第几位。

| 排序方式 | HR@10 | NDCG@10 | MRR |
| --- | --- | --- | --- |
| A. 直接用召回分数排序 | 0.0292 | 0.0137 | 0.0124 |
| B. DIN 重新排序 | 0.0267 | 0.0113 | 0.0098 |
| 差值（B − A） | −0.0025 | −0.0025 | −0.0026 |

分母是全部 56,440 个验证集用户，目标没被召回的记 0 分。

**两个结论**：

1. **召回天花板 Recall@50 = 10.34%，但只用召回分数排序只兑现了 2.92%**——中间空了 7 个百分点，
   理论上排序层有很大空间。而 DIN 不但没利用上，还退到了 2.67%。
   只看被召回的 5,835 个样本（条件口径）：A 的 HR@10 = 28.24%，B = 25.84%。
2. **原因很可能是训练分布和推理分布不一致**：排序模型训练时的负样本是**从全库随机抽**的，
   跟正样本差别巨大、很容易区分；而推理时候选是召回出来的 top-50，全都是"用户可能喜欢"的物品，
   难度高得多。模型没学过怎么在这些相似候选之间排序。
   业界对这件事的标准解法是**用召回结果做难负样本重训排序层**（见「后续计划」）。

这也是为什么要把两阶段串起来评一次：只看 6.3 那张 AUC 表，会觉得排序层"差不多能用"；
串起来才发现它连召回层自己给的顺序都没跑赢。

### 6.5 可以写进面试的结论

1. **余弦训练显著优于内积训练**：Recall@50 从 6.74% 提升到 9.42%（+2.67pp，配对 bootstrap p<0.001）。
   但 AUC 反而下降（0.8679→0.8139）——两个指标的评估口径不同，优化方向可以相反。
2. **"取最近一个物品"不如"平均所有历史"**：6.28% vs 6.74%（−0.46pp，显著变差）。
   说明单一行为信号方差大，平均能降噪。
3. **归一化的收益依赖训练步数**：200k 数据训 3 轮时余弦只有 6.42%（低于同数据 baseline 的 8.81%），
   训到 10 轮回到 8.63%。因为归一化后模型要学的是"方向"，比"模长"难学。
4. **指标提升要连带看热门偏差**：余弦版 Recall 最高，但它的召回结果里热门片占 52%
   （baseline 只有 24%，全库 2.6%）。指标提升里有一部分来自"更精准地推热门"，
   上线需要额外监控多样性和长尾覆盖。
5. **排序层的注意力没有带来提升**：【待填，一句话，跟 6.3 的结论保持一致】

## 八、如何运行

```bash
# 0. 下载 MovieLens-1M 并解压到 data/ml-1m/

# 1. 生成训练样本
python prepare_data.py

# 2. 训练召回层双塔并导出向量
python two_tower.py

# 3. 跑 Faiss 检索 + 多实验对比
python recall_eval.py

# 4. （可选）看召回结果的热门占比
python hot_ratio.py

# 5. 训练排序层 DIN（会先跑自检，不通过直接退出）
python din.py

# 6. 端到端评估：召回 top-50 → 排序重排
python rank_eval.py
```

也可以直接 `./run_all.sh` 一键跑完 1-6 步（全量数据约 30-40 分钟）。

## 九、实现中的一个坑（值得记录）

**PyTorch 和 faiss-cpu 在 macOS 上不能放在同一个进程里**：两者各自链接了一份 OpenMP 运行时，
先后使用会直接崩（退出码 134/139），而且**没有任何 Python 报错**。

实测 `faiss.omp_set_num_threads(1)` 和 `KMP_DUPLICATE_LIB_OK=TRUE` 都无效。

**解决方案是把训练和检索拆成两个进程**——训练只负责导出向量，检索进程只 import numpy + faiss。
这本来也是工业界的标准架构（离线训练 / 在线检索服务分离）。

## 十、已知局限

- 物品塔只用了 ID，没有用物品的文本/类目特征
- 用户塔只用了平均池化。候选相关的注意力加权（DIN）需要用户塔看到候选物品，
  那就不再是双塔（用户向量无法离线预计算、Faiss 召回失效），所以放到排序层实现
- **用户历史只保留最近 3 条**，DIN 的"从长历史里挑出相关的几个"几乎没有发挥空间
  （实测：历史长度均值 2.96，训练后注意力的有效个数 ≈ 2.7，接近均匀的 3.0）
- **排序层的训练负样本是全库随机抽的，和推理时的召回候选分布不一致**（见 6.4），
  这是排序层在端到端评估里没跑赢召回分数的可能原因
- 排序层用内积打分，而不是 DIN 原论文的「用户向量与候选向量拼接后过 MLP」，
  这是为了和召回层复用同一套训练/评估代码
- 负采样只用随机负样本，没有引入难负样本
- 没有做超参搜索，`EMB_DIM` / `EPOCHS` 等超参都是凭经验设的

## 十一、后续计划

- ✅ 补上排序层（DIN），并把召回和排序串成端到端链路（6.4）
- **用召回出来的 top-50 当难负样本重训排序层**——这是让排序层真正跑赢召回分数的第一步，
  也是 6.4 那个负面结果最直接的改进方向
- **加长用户历史序列**（当前只有 3 条），并做历史长度的消融——这是让 DIN 真正发挥作用的必要前提
- 物品塔加入文本特征（标题/类目），提升冷启动能力，同时给排序层提供更丰富的候选特征
- 补充超参搜索（`EMB_DIM` / `EPOCHS` / 负采样比例）
