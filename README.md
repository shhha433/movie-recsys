# 双塔召回 + DIN 排序的推荐系统

## 项目简介

在 MovieLens-1M 上实现一条完整的**两阶段推荐链路**：双塔模型从全库召回 top-50，
DIN 对这 50 个候选重新排序。整条链路可以一键复现，并且用**端到端指标**而不是"模型各自的 AUC"来评估。

**主要结果**：

| 环节 | 指标（口径） | 结果 | 随机基线 |
| --- | --- | --- | --- |
| 召回 | Recall@50（全库 3883 选 50） | **12.10%** | 1.29%（9.4 倍） |
| 排序 | test AUC（1 正 + 4 随机负） | **0.8076** | 0.50 |
| **端到端** | **HR@10（召回 top-50 → 排序重排）** | **5.88%** | 0.26%（22.8 倍） |

三层口径不同，不能横向比较——只有**端到端**那一行是"线上会看到的数"。
排序层把召回命中的 12.10% 兑现成 5.88%，**兑现率 48.5%**；不排序只有 19.8%。

## 一、数据集

| 项目 | 说明 |
| --- | --- |
| 名称 | MovieLens-1M（GroupLens / 明尼苏达大学） |
| 来源 | https://grouplens.org/datasets/movielens/1m/ |
| 内容 | 6040 位真实用户、3883 部电影、100 万条真实评分（2000–2003 年） |
| 正样本定义 | 评分 ≥ 4 视为"喜欢" |
| 切分方式 | **按时间切分**：前 80% 训练 / 中 10% 验证 / 后 10% 测试 |

**为什么按时间切分**：随机切分会让模型在训练时"看到未来"，离线指标虚高、上线就崩。

### 样本构造

把每位用户的观影序列滑窗成 `(历史, 目标, 标签)` 三元组：

```text
序列：[M1, M2, M3, M4, ...]
   历史 "M1"          → 目标 M2    label 1
   历史 "M1"          → 目标 M77   label 0（随机负样本）
   历史 "M1 M2 ..."   → 目标 M3    label 1
   ...
```

- **历史保留最近 20 个物品**，左补 0 补齐到 20 列
- 正负样本 1 : 4
- 最终训练样本 **2,274,230 条**

## 二、整体架构（6 步流水线）

```text
prepare_data.py          原始评分 → train/valid/test.csv
        ↓
two_tower.py             训练召回模型 → 向量 + model_two_tower.pt
        ↓
recall_eval.py           Faiss/向量检索 → Recall@50
        ↓
build_hard_negatives.py  用召回 top-50 挖难负样本 → train_hard.csv
        ↓
din.py                   训练排序模型（吃 train_hard.csv）→ model_din.pt
        ↓
rank_eval.py             召回 top-50 → 排序重排 → HR@10 / NDCG@10 / MRR
```

全部可以 `./run_all.sh` 一键跑完。

**为什么必须分两个阶段**：双塔的用户向量必须与候选无关，才能离线预计算、建索引、用 ANN 检索；
而排序层的候选是输入的一部分，用户表示可以随候选变化。两层能做的事不同，代价也不同。

---

## 三、召回层：双塔模型

```text
历史序列 [B, 20] → 物品 Embedding → 平均池化 → MLP → 用户向量 [B, 32]
                                                        ↘ 内积 → 分数
候选物品 [B]    → 物品 Embedding →        MLP → 物品向量 [B, 32]
```

**关键设计点**：

1. **两塔共用同一张物品 Embedding 表**——历史和候选是同一批物品
2. **`padding_idx=0`**：第 0 行恒为 0 且不参与训练，平均池化时 padding 天然无贡献
3. **用户塔看不到候选**——这是双塔的定义，否则用户向量无法离线预计算
4. **训练 10 轮**：3 轮时 valid AUC 还在每轮 +0.01 上涨，明显欠拟合

## 四、排序层：DIN

### 4.1 为什么召回层不能用注意力

用户塔算用户向量时**看不到候选物品**——这是双塔能离线预计算的前提。
所以召回层只能用「与候选无关」的池化：平均、最近 N 个、时间衰减。

排序层候选是输入之一，用户表示可以随候选变化——DIN 的注意力就建立在这个自由度上：
**要猜他喜不喜欢这部科幻片，就重点看他看过的科幻片。**

### 4.2 注意力怎么算

1. 历史向量 `h ∈ [B, L, d]`，候选向量 `q ∈ [B, d]`
2. 打分网络（两层 MLP）吃三段拼接 `[候选, 历史, 候选 − 历史]` → 每个历史位置的分数 `[B, L]`
3. padding 位置先置 `-inf` 再 softmax → 权重；用它加权求和 `h`

**两个坑**：mask 必须在 softmax **之前**（否则剩余权重和不再是 1）；
`padding_idx=0` 让 padding 的 `h` 是零向量，不 mask 会把真实位置的权重和压到小于 1。
`din.py` 带自动自检，不通过就不进训练。

### 4.3 难负样本：这一步决定了排序层有没有用

排序层如果只用全库随机负样本训练，会遇到 **train-serving skew**：训练时负样本跟正样本差得远，
推理时面对的却是召回出来的相似候选，模型没学过怎么在"鸡蛋里挑骨头"。

`build_hard_negatives.py` 用召回 top-50 挖负样本，但有一条关键规则：

> **只在目标物品被召回时（12.10% 的样本）才用召回候选当负样本，其余退回随机负样本。**

因为目标没被召回时，top-50 全是"召回模型认为用户会喜欢的物品"。把它们当负样本，
等于教模型"召回候选 = 负"——实测这样训出来的模型 AUC 从 0.85 崩到 0.53，端到端还不如不排序。

本次重建：难负样本 59,568 组 / 随机负样本 395,278 组（13.1% 用上了难负样本）。

## 五、评估方式

| 指标 | 怎么算 | 用在哪 |
| --- | --- | --- |
| **AUC** | 1 正 + 4 随机负上的排序质量 | 召回层、排序层 |
| **Recall@50** | 全库 3883 里检索 top-50，看目标是否命中 | 只有召回层 |
| **HR@10** | 目标是否进了前 10（0/1 平均） | 端到端 |
| **NDCG@10** | 目标排第 r 名得 `1/log₂(r+1)`，越靠前越高 | 端到端 |
| **MRR** | 目标排第 r 名得 `1/r` | 端到端 |

**HR / NDCG / MRR 的区别**：HR 只看"进没进前十"；NDCG 关心位置但用对数衰减（前 3 名权重高）；
MRR 衰减最陡（第一名满分、第二名砍半）。首页只有 10 个位置，**NDCG 最接近真实业务价值**。

**两种口径**：
- **端到端**：分母是全部 56,440 个验证用户，目标没被召回的记 0 分 → 模拟线上
- **条件口径**：只看被召回的样本 → 衡量排序层本身的强弱
- 关系：`条件口径 = 端到端 ÷ Recall@50`

**训练用的 loss 和这些指标是两回事**：双塔和 DIN 都用 `BCEWithLogitsLoss`，只在训练集上算，
是唯一的训练信号；AUC / Recall / HR 不参与参数更新。

## 六、实验结果

### 6.1 召回层

| 指标 | 结果 |
| --- | --- |
| valid AUC | 0.9082（第 10 轮） |
| test AUC | **0.8813** |
| Recall@50 | **12.10%**（95% CI [11.85%, 12.39%]，6832 / 56440） |
| 随机基线 | 1.29% |

训练曲线（valid AUC）：0.8478 → 0.8566 → 0.8658 → 0.8765 → 0.8855 →
0.8928 → 0.8981 → 0.9025 → 0.9057 → **0.9082**，第 10 轮仍在涨。

### 6.2 召回层消融（待重跑）

> ⚠️ 重建前（历史长度 3、3 轮训练）做过 4 组对照实验 + 配对 bootstrap，
> 结论是"余弦训练显著优于内积"（+3.80pp，p<0.001）。
> 重建后数据变了，这批数字作废，需要重跑。
>
> 重跑方法：改 `two_tower.py` 顶部的 `POOLING` / `USE_COSINE` 开关，各跑一次 `two_tower.py`，
> 最后跑 `recall_eval.py` 自动出对比表。

| 实验 | `POOLING` | `USE_COSINE` |
| --- | --- | --- |
| baseline（已跑） | `"mean"` | `False` |
| A 取最近一个 | `"last"` | `False` |
| B 余弦 | `"mean"` | `True` |
| C mask 写法 | `"mask"` | `False` |

### 6.3 排序层

训练数据换成难负样本后（10 轮）：

| 指标 | 结果 |
| --- | --- |
| valid AUC | 0.8488 |
| test AUC | **0.8076** |

比随机负样本训练时的 0.8502 低，**这不是退步**——口径变了：模型不再针对"随机负样本"优化，
AUC 只在 1 正 + 4 随机负上算，而训练时见到的多是难负样本。排序层的真实价值看 6.4。

### 6.4 端到端：召回 top-50 → 排序重排

召回天花板 Recall@50 = **12.10%**。

| 排序方式 | HR@10 | NDCG@10 | MRR |
| --- | --- | --- | --- |
| A. 直接用召回分数排序 | 0.0239 | 0.0104 | 0.0102 |
| **B. DIN 重新排序** | **0.0588** | **0.0295** | **0.0241** |
| 差值（B − A） | **+0.0349** | **+0.0192** | **+0.0138** |

分母是全部 56,440 个验证用户，目标没被召回的记 0 分。

条件口径（只看被召回的 6,832 个样本）：

| 排序方式 | HR@10 | NDCG@10 | MRR |
| --- | --- | --- | --- |
| A. 直接用召回分数 | 0.1975 | 0.0856 | 0.0847 |
| **B. DIN 重新排序** | **0.4854** | **0.2439** | **0.1989** |

**三个结论**：

1. **召回决定天花板，排序决定兑现率。** 排序层的 HR@10 不可能超过 Recall@50（它只能在 50 个候选里挑），
   但同样是这批候选，"直接用召回分数"只兑现 19.8%，DIN 重排后兑现 **48.5%**——指标翻了 2.5 倍。
2. **难负样本必须"目标被召回"时才用。** 对所有样本都用召回 top-K 当负样本时，93% 的样本里
   正样本根本不在候选里，等于教模型"召回候选 = 负"，AUC 崩到 0.53。改成条件采样后恢复正常。
3. **训练和推理的候选分布必须一致。** 随机负样本训出来的模型在随机负上 AUC 0.85，
   到真实候选上却打不过召回分数——这就是 train-serving skew。

### 6.5 可以写进面试的结论

1. **端到端 HR@10 从 2.39% 提升到 5.88%**（相对 +146%），NDCG@10 从 1.04% 到 2.95%。
2. **把历史长度从 3 加到 20、训练从 3 轮加到 10 轮**，召回 Recall@50 从 6.76% 提到 **12.10%**，
   双塔 test AUC 从 0.8511 提到 0.8813——说明之前的瓶颈是**行为信号太短 + 欠拟合**，不是模型结构。
3. **排序层不能直接超过召回天花板**：5.88% < 12.10%，这不是失败，是两阶段分工的本质。
4. **AUC 高 ≠ 端到端好**：排序层在随机负上 AUC 0.81，端到端却要靠难负样本训练才有价值。

## 九、实现中的坑

**PyTorch 和 faiss-cpu 在 macOS 上不能同进程**：两者各带一份 OpenMP，先后使用会静默崩溃
（退出码 134/139、无 Python 报错）。实测 `faiss.omp_set_num_threads(1)` 和
`KMP_DUPLICATE_LIB_OK=TRUE` 都无效。方案是训练与检索拆进程——这也正是工业界
离线训练 / 在线检索分离的架构。`rank_eval.py` 因此用 numpy 暴力检索（3883 个物品只要 2 秒），
不 import faiss。

## 十、已知局限

- 物品塔只用了 ID，没有用类目（`genres`）、标题等特征；这也是 DIN 注意力可发挥空间有限的原因
- 负采样仍是随机 + 难负样本的简单组合，没有做 popularity 去偏
- 排序层用内积打分，而不是 DIN 原论文的「用户向量与候选向量拼接后过 MLP」
- 召回只有 12.10%，意味着 88% 的目标物品压根没进候选集；瓶颈在召回覆盖率，不在排序
- 消融实验（6.2）尚未在重建后的数据上重跑
- 没有做超参搜索，`EMB_DIM` / `EPOCHS` / 学习率都是凭经验设的

## 十一、后续计划

- 重跑 6.2 的 4 组消融，把 `POOLING` / `USE_COSINE` 的结果补回来
- 物品塔加入 `genres` 多热特征，让同类型电影共享表示，提升冷启动物品覆盖率
- 排序层改成「用户兴趣向量 + 候选向量拼接过 MLP」，对齐 DIN 原论文
- 引入 popularity 去偏，监控召回结果的多样性
